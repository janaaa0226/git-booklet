The problem Git solves

Imagine you are building a website. You make changes, and suddenly something breaks. You want yesterday's working version back. Without a system, people end up with this:

A familiar mess
website
website-final
website-final2
website-final-real
website-final-real-actually-working

Now add a friend who edits the same files. Who has the latest version? Whose changes win? Git exists to solve both problems.

Git is a program that tracks changes in your project over time.

What is Git?

What is it?

Git is a program on your computer. It watches a project folder and lets you save checkpoints, like save points in a game. (Tools like this are formally called version control systems.)

What does it do?

  • Remembers every checkpoint you save, and what changed in each.
  • Lets you go back to an earlier checkpoint.
  • Lets several people work on one project without overwriting each other.

Two words you will need

A repository (or repo) is a project folder that Git is tracking, together with its history. A commit is one saved checkpoint. That's all they mean.

Git works entirely on your computer, with no internet and no GitHub.

What is GitHub? (Git vs GitHub)

GitHub is a website that stores Git repositories online so you can back them up, share them, and work with other people.

GIT: "Tracks my project"GITHUB: "Stores and shares my Git project online"
A programAn online service
Runs on your computerRuns in a browser at github.com
Tracks changes, creates commits, keeps historyStores repositories, supports collaboration, lets people review changes
How they work together
YOUR COMPUTER
     |  Git tracks changes here
LOCAL REPOSITORY
     |  git push (send)   ^ git pull (receive)
     v                    |
GITHUB  =  REMOTE REPOSITORY

Analogy: Git is like Word's version history on your machine. GitHub is like Google Drive, the shared place online.

Git and GitHub are not the same thing. You can use Git without GitHub, but GitHub is useless without Git.
Quick check: which one runs on your computer?

Git. GitHub is the website.

The big picture

Before any command, look at the whole system once. Every command in this course moves your work one step along this path.

The path your work takes
YOUR PROJECT
   |
WORKING DIRECTORY   the files you are editing right now
   |  git add
STAGING AREA        the changes you picked for the next commit
   |  git commit
GIT HISTORY         your saved checkpoints (commits)
   |  git push
GITHUB              the online copy
git add and git commit happen only on your computer. Nothing reaches GitHub until git push.

Your first project and git init

Setup (once)

Install Git from git-scm.com, and VS Code from code.visualstudio.com. A terminal is a text box where you type instructions. In VS Code open it with Ctrl + `. Check Git works:

Check Git
git --version

You should see something like git version 2.45.0. Then tell Git who you are, so checkpoints carry your name:

Set your identity
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Create the project

Make a folder called MyFirstGitProject, put a file hello.txt containing "Hello, Git!" inside, and open the folder in VS Code (File → Open Folder).

Our project
MyFirstGitProject/
└── hello.txt

git init

You have a folder, but Git isn't tracking it yet. init means initialize.

Tell Git to start tracking
git init

In simple words: "Git, start tracking this project." Git creates a hidden .git folder, which is where it keeps the history. Never edit or delete it.

You should see: Initialized empty Git repository in .../MyFirstGitProject/.git/

Terminal says git is not recognized? Close and reopen VS Code, or reinstall Git.

git status

When you are confused, run git status.
Ask what is happening
git status

In simple words: "Git, tell me what is happening right now."

Example output
On branch main
No commits yet
Untracked files:
        hello.txt

On branch main is the line of work you are on. Untracked means Git sees the file but isn't saving its history yet. Later you will also see modified (changed since the last checkpoint) and staged (chosen for the next commit).

fatal: not a git repository means your terminal is in the wrong folder. Use cd MyFirstGitProject, or run git init if you skipped it.

git add and staging

What is it, and why?

Say you changed three files, hello.txt, README.md and image.png, but only want the first two in your next checkpoint. The staging area is where you choose them. Think of packing a box before sealing it.

Stage one file
git add hello.txt
Stage everything that changed
git add .

The dot means "everything in this folder". Now run git status.

Output
Changes to be committed:
        new file:   hello.txt

The heading changed from "Untracked" to "Changes to be committed", so the file is staged.

git add does NOT upload anything and does NOT save a checkpoint. It only prepares changes for the next commit.
Quick check: you edited Main.java. What comes before committing?

git add. It tells Git which changes to include.

git commit

A commit is a save point. Everything you staged becomes one checkpoint.

Save the checkpoint
git commit -m "Add hello file"
gituse Git
commitcreate a saved checkpoint
-m"here comes my message"
"Add hello file"describes the checkpoint
Output
[main (root-commit) 3f2a9c1] Add hello file
 1 file changed, 1 insertion(+)

Good messages say what changed: Add welcome message, Fix typo in README. Bad ones: stuff, final. You will read these in a month.

nothing to commit isn't an error. It means no new changes. If you see pathspec did not match, you probably typed - m or m. It must be -m, joined, with straight quotes.

Git history

Edit hello.txt (add a line), then repeat the loop twice: git add ., git commit -m "Update welcome message". Now look back:

Show my checkpoints
git log --oneline
Output
a81c7d2 Update welcome message
5b09e13 Create README
3f2a9c1 Add hello file

Each line is a commit: a short ID, then your message. Newest is on top. Git remembers all of them.

See exactly what changed (before staging)
git diff

Lines starting with + were added, and - were removed. Press q to leave the view.

Create a GitHub repository

So far, everything is on your computer. Now we make a place online. On github.com click + → New repository.

  • Name: MyFirstGitProject.
  • Public means anyone can see it. Private means only you and people you invite.
  • Do not tick "Add a README" or a license here. Your project already has files, and adding them online makes the two copies disagree.

Click Create repository. GitHub shows you a URL like https://github.com/YOURNAME/MyFirstGitProject.git. Keep it open.

Connect to GitHub: remote, origin, push

git remote add origin

A remote is another copy of your repo stored elsewhere, here on GitHub.

Connect the two
git remote add origin https://github.com/YOURNAME/MyFirstGitProject.git

origin is only a nickname for that GitHub repository, so you don't retype the long URL. Check it any time:

Which GitHub repo am I connected to?
git remote -v

git push

Send your commits to GitHub
git push -u origin main
git pushsend my commits
originto my GitHub repo
mainfrom my main branch
-uremember this link, so later git push alone is enough

You should see Writing objects: 100% and branch 'main' set up to track 'origin/main'. Refresh GitHub and your files are there. A browser window may ask you to sign in. That's normal, since GitHub no longer accepts your password in the terminal.

remote origin already exists: it's already connected, so check with git remote -v. Could not resolve host: no internet connection to github.com (check VPN or school network). Your commits are safe.

git pull and the everyday workflow

git pull means "get the latest changes from GitHub onto my computer." Use it before you start working, or when someone else (or you, on another computer) changed the project.

The everyday loop
git pull                     # get the latest
# ...edit files...
git status                   # what changed?
git add .                    # choose changes
git commit -m "What I did"   # save a checkpoint
git push                     # send it to GitHub
Git saysMeaningYou do
ahead of 'origin/main'You have commits GitHub doesn'tgit push
behind 'origin/main'GitHub has changes you don'tgit pull

Branches

Imagine main is your safe, working version. You want to try a new feature without risking it. So you create a separate branch, work there, and when you're happy you merge it back.

Picture
main      o---o---o-----------o   (merge)
                   \         /
new-feature         o---o---o
Create a branch and move onto it
git switch -c new-feature

In our project, create notes.txt, then git add . and git commit -m "Add notes file". Switch back and look:

Move between branches
git branch
git switch main

git branch lists branches (a * marks where you are). After switching to main, notes.txt disappears from your folder. It's safe on the other branch. Older tutorials use git checkout to switch. It does the same job.

Merging

Merging means "combine changes from another branch into the branch I'm on." You go to the branch that should receive the work.

Bring new-feature into main
git switch main
git merge new-feature
git branch -d new-feature

notes.txt is now on main. The last line deletes the finished branch, and your commits stay.

Merge conflicts

Person A changes line 1 of hello.txt to "Hello from A". Person B changes the same line to "Hello from B". Git can't decide which to keep. That is a conflict. Your project is not destroyed. Git is asking you to decide.

What you'll see in the file
<<<<<<< HEAD
Hello from A
=======
Hello from B
>>>>>>> new-feature

<<<<<<< starts your version, ======= separates the two, >>>>>>> ends the other. (HEAD = where you are now.)

  1. Open the file and decide what the final text should be.
  2. Delete the three marker lines and keep only the text you want.
  3. Save the file.
  4. git add hello.txt
  5. git commit (accept the default message).

VS Code shows Accept Current / Incoming / Both buttons above the conflict that do the editing for you.

Clone and pull requests

git clone means "copy an existing GitHub repository onto my computer." You use it once, to start. It downloads everything and sets up origin for you.

Download a project
git clone https://github.com/USER/project.git

A pull request (PR) is a GitHub feature. It says: "I made changes on my branch. Can we review them and merge them?" Push your branch (git push -u origin new-feature), click Compare & pull request on GitHub, describe the change, let others review, and click Merge. To contribute to someone else's project, click Fork first to get your own copy.

.gitignore

A file named .gitignore tells Git which files not to track: editor settings, generated files, and secrets.

Example .gitignore
.env
*.class
.vscode/
node_modules/
Never commit passwords, API keys or private secrets. Once pushed, treat them as public.

Your Git identity (user.name and user.email) is the name stamped on commits. Your sign-in (the GitHub account VS Code uses) decides who may push. They're related but separate. Check the first with git config user.email and where you push with git remote -v.

Git error? Don't panic.

Errors usually mean Git needs clarification. They almost never mean your work is gone.

MessageMeaning and fix
not a git repositoryWrong folder. cd into your project.
remote origin already existsAlready connected. git remote -v; to change: git remote set-url origin NEW_URL
nothing to commitNo new changes. Usually fine.
push rejectedGitHub has newer work. git pull, fix any conflict, then push. Don't force it.
Could not resolve hostNo connection to github.com. Check internet or VPN.
pathspec did not matchA typo, like - m instead of -m, or a wrong file name.

Undoing changes safely

SituationSafe fix
Changed a file, not committed, want it backgit restore file (your unsaved edits are lost for good)
Staged by accidentgit restore --staged file (edits stay)
Typo in last commit message (not pushed)git commit --amend -m "New message"
A commit I don't likegit revert ID adds a new commit that cancels it (find ID with git log --oneline)
Pushed something wronggit revert, then push
git reset --hard permanently deletes uncommitted work. git push --force overwrites GitHub's history and can erase teammates' work. Avoid both until you fully understand them.

Beginner practice scenarios

1. I changed my code and want to save it. git status, git add ., git commit -m "...", git push.

2. I want to upload an existing project. git init, add and commit, create an empty GitHub repo, git remote add origin URL, git push -u origin main.

3. I want someone's project on my computer. git clone URL.

4. My friend changed the project. git pull.

5. I want to experiment safely. git switch -c my-experiment.

6. Which GitHub repo is this? git remote -v.
